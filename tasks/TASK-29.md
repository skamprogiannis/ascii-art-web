# TASK-29: Audit Export Headers & Multi-Format Downloads

**Status:** COMPLETED
**Priority:** P2 (Medium)
**Dependencies:** TASK-28
**Estimated Time:** 60 minutes

## Objective

Make the export flow audit-friendly by moving downloads to the backend, adding multiple export formats, and ensuring the project uses `Content-Type`, `Content-Length`, and `Content-Disposition` correctly.

## Requirements

1. Keep the implementation standard-library only.
2. Add a server-backed export route for downloadable files.
3. Support `.txt`, `.html`, and `.json` exports.
4. Ensure export responses set `Content-Type`, `Content-Length`, and `Content-Disposition`.
5. Keep the export action clear in the UI.
6. Add test coverage for export headers and payloads.
7. Update documentation to explain the HTTP headers used for downloads.

## Implementation Steps

- ✅ Added `POST /export` for downloadable ASCII art files.
- ✅ Implemented `.txt`, `.html`, and `.json` export payload generation from the existing render pipeline.
- ✅ Set explicit `Content-Type`, `Content-Length`, and `Content-Disposition` headers on export responses.
- ✅ Buffered HTML and JSON responses so the application returns explicit `Content-Length` values on rendered output too.
- ✅ Updated the UI to let users choose an export format before downloading.
- ✅ Added Go handler tests for export success and invalid-format failures.
- ✅ Updated the README and project tracking files with the completed audit/export work.

## Acceptance Criteria

- [x] The project offers a clear export action in the UI.
- [x] `.txt`, `.html`, and `.json` exports are available.
- [x] Export responses use `Content-Type`, `Content-Length`, and `Content-Disposition`.
- [x] Exported files are generated by the backend rather than only in the browser.
- [x] Handler tests cover export headers and payload validity.
- [x] Documentation explains the purpose of the download headers.
